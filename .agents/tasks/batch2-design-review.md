## Findings

### 1. MEDIUM — The pinned migration header and acceptance 1 name Django 5.2.17, but the installed Django is 5.2.18

Where: §4.1 ("Django 5.2.17 header", the pinned `0002_alter_run_status.py` whose first line is `# Generated by Django 5.2.17 on <date>`), §2 acceptance 1 ("matches the file pinned in §4.1 (header date aside)"), and the hand-write fallback ("hand-write exactly this file").

Evidence:
- `backend/.venv/bin/python -c "import django; print(django.get_version())"` prints `5.2.18`. The venv has `django-5.2.18.dist-info`.
- `pyproject.toml:22` pins `Django>=5.2,<5.3`.
- Only the existing `0001_initial.py` says 5.2.17, because it was generated earlier.

So `makemigrations runs` will write `# Generated by Django 5.2.18 on …`. Acceptance 1 only excuses the date, so a correctly generated file fails it as written. That leaves the implementer two bad choices: hand-edit a generated file to fake an older version, or report a false failure. The fallback would also put a false provenance line on a hand-written file.

Fix: in §4.1 and acceptance 1, change the rule to "matches the pinned body, i.e. everything from `from django.db import …` onward; the whole `# Generated by …` line is excluded from the comparison". In the pinned block, write the header as `# Generated by Django <installed version> on <date>`. For the fallback, add: "hand-written file header: `# Generated by Django 5.2.18 on <date>` using the version `django.get_version()` reports in `backend/.venv`, and the final report says it was hand-written".

### 2. NIT — 6(c) rewrite does not say how each single pass ends

Where: §4.5, "6(c)", steps 1 and 2 ("Iterate `bare.read_output()` once", "a single pass over `guarded.read_output()`").

`InteractiveExec.read_output` (`sandbox.py:350-391`) only ends on EOF/`OSError` or `socket.timeout`. The current test bounds each pass with `if "done" in line: break`. "Iterate once" could be read as one `next()` (which may yield the echo or not, depending on framing) or as a loop until EOF.

Fix: state that each pass is `for line in handle.read_output(): lines.append(line); if "done" in line: break`, as the current test does at `test_sandbox_execution.py:1206-1209` and `:1222-1225`. `flush_remaining()` is appended to the guarded output only. Keep both `exec_interactive` calls without `timeout_s`, as today. The `sh -c "read value; echo done"` process exits after `done`, so EOF also ends the pass.

### 3. NIT — Stale fixture comment in `RunHistoryView.test.jsx`

Where: §4.6 keeps the shared `RUNS` array unchanged (correct). But its comment at `RunHistoryView.test.jsx:56` says "One Run per Run_Status in `Run.STATUS_CHOICES` (Requirement 11.2)". That becomes false once `failed` is the sixth choice.

Fix: reword it to "One Run per Run_Status other than `failed`, which has its own test below, …". Wording only. Add it to the list of docstrings and comments rewritten in the same change.

## Verified assumptions

- **No PATCH or create overrides today.** `RunViewSet` has no `partial_update` or `perform_create` override. `get_serializer_class` maps `update`/`partial_update` → `RunUpdateSerializer`. `http_method_names` excludes `put` (`views.py`). `RunUpdateSerializer` has no `update` override. DRF 3.18.3's `ModelSerializer.update` ends in a bare `instance.save()` (`rest_framework/serializers.py:1064`).
- **POST takes a client `run_id` today.** `run_id` is writable on `RunSerializer`, with no format check (`serializers.py:62-78`). The model has `CharField(max_length=64, unique=True)` (`models.py:72`). `status` is writable on create and defaults to `running` (`models.py:75`).
- **Duplicate-message text.** `get_unique_error_message` (`field_mapping.py:331-338`) formats Django's `unique` message as "run with this run id already exists.". `UniqueValidator.__init__(queryset, message=None, lookup='exact')` accepts `message`.
- **`extra_kwargs` behaviour.** `get_extra_kwargs` deep-copies `Meta.extra_kwargs`, so `RunUpdateSerializer` inheriting it cannot mutate `RunSerializer`'s copy. For the read-only `run_id` on PATCH, the validators are never run. Model `MaxLengthValidator` is filtered out of the derived validators, and `CharField` re-adds max_length itself, so replacing `validators` loses nothing.
- **Race path.** A duplicate insert raises `django.db.IntegrityError` from the real Mongo unique index (`test_mongodb.py:350-356`). `settings.py` has no `ATOMIC_REQUESTS`.
- **`apply_decision` pattern.** It is `retry_on_transient_transaction_error(fn)` with `django_mongodb_backend.transaction.atomic()` and a conditional `filter(...).update(status=..., updated_at=to_mongo_precision(now))`. Zero rows raises `StateTransitionError(_stored_status_of(run))`. `StateTransitionError` is not retried (`mongodb.py:126-170`, `DEFAULT_TRANSACTION_ATTEMPTS = 5`). Today's `__init__` takes `(current_status, *, recorded_decision=None)`.
- **`running → awaiting_review` is written nowhere today.** Only docstrings mention it: `RunUpdateSerializer` and `tasks/scheduled.py:193`. `submit.py:1219` PATCHes only `pr_url`.
- **Upload order.** It is events → diff → screenshots (`uploader.py:529-531`).
- **Uploader helpers.** `_post` catches `(httpx.HTTPError, httpx.InvalidURL)` (`:870`). `validate_run_id` is imported and wrapped in `upload_run` (`:507`). `_auth_headers`, `_error_detail` and `_build_url` exist. `submit.py:260` imports from `uploader`, and `submit.py:314` defines its own `RUN_DETAIL_PATH_TEMPLATE`.
- **`run` pipeline layout.**
  - Step 3 (`_build_run_credential_file`), step 4 and step 5 (`docker.from_env` → ClickException) sit before the inner `try`.
  - `Sandbox(run_id, client)` sits between them. The inner `finally` runs `sandbox.teardown()` and then the echo.
  - `_upload_run_artifacts(run_dir, run_id, backend_url)` is called after it and calls `load_token` internally.
  - So an outer `try` opened after 2b covers steps 3–10, and teardown runs before the outer handler.
- **Interactive auth.** `click.prompt` is at `cli.py:927`, `except KeyboardInterrupt → AuthError` at `:969`, and the `timed_out` check at `:949` runs before `if not asked`. So the 6(d) fake (`prompt_lines=["Signing in..."]`, `timed_out=True`) reaches the "produced no further output … abandoned" message. `_FakeInteractiveExec.timed_out` exists (`test_interactive_auth.py:105`).
- **Run-id grammar.** `run_directory._RUN_ID_PATTERN = \A[A-Za-z0-9][A-Za-z0-9_-]{0,63}\Z` (`:157`), and `EVENT_LOG_FILENAME = "events.jsonl"`.
- **Config.** `config._optional_text` exists. `ProjectConfig` ends with the defaulted `project_dir: str = ""`, so a trailing defaulted `project` field is safe.
- **6(b) test inputs.** `git_capture` reads `MAX_DIFF_REQUEST_BYTES` at call time (`:640`). The overflow message contains "`{n} changed files`" and "`(MAX_DIFF_REQUEST_BYTES)`" (`:642-648`). `resolve_diff_base` exists (`:696`).
- **Test call sites.** The `run` call sites listed in §4.5 match the files: `test_cli.py` `_RUN_ARGS` uses, `test_interactive_auth.py`, and the four `test_sandbox_execution.py` argvs. No other CLI test file invokes `run`. The only `run` test that makes `load_token` fail is `test_cli.py:665`.

- **6(c) contract.** `InteractiveExec.read_output()` takes no parameters, and `send_line` arms redaction (`sandbox.py:334-391`). `_REDACTED = "***"`. Raw-socket access via `getattr(socket, "_sock", socket)` is the module's own idiom.

- **Wrong:** the Django version in the migration header is 5.2.17. The installed version is 5.2.18 (Finding 1).
- **Unverified, with a planned test:** that `Model.save(update_fields=[...])` under `django_mongodb_backend` 5.2.4 issues a `$set` of only those fields. The D4 stale-status DB test checks this directly.
