## Before-behaviour facts the final report must state (verified in design §1 and at planning)

- POST `/api/runs/` already takes a client-supplied `run_id` (required writable field on
  `RunSerializer`); only length ≤64 and uniqueness are checked, no format check
  (`backend/runs/serializers.py` "run_id format is not validated here", `models.py` `CharField(max_length=64, unique=True)`).
- Duplicate `run_id`: sequential → 400 `{"run_id": ["run with this run id already exists."]}`
  (DRF-derived `UniqueValidator`); concurrent race → unique-index `IntegrityError` → unhandled 500.
- `running → awaiting_review` is written nowhere today (backend or CLI); only docstrings
  (`RunUpdateSerializer`, `backend/tasks/scheduled.py:193`) claim the CLI does it.
- CLI upload order is events → diff → screenshots (`cli/vaultshield/uploader.py:529-531`), so
  the completion signal lives in a CLI `PATCH status=awaiting_review` after `upload_run`
  returns (after screenshots), gated in the view in `apply_decision`'s conditional atomic
  style — not in the diff view (design D3, §7 item 9).
- PATCH accepts any status choice today; create may set any status; authz is token-only, no owner model (flagged, unchanged).
- The CLI touches the backend only at step 10 today (`_upload_run_artifacts`, `cli.py:828`), so a fresh run 404s.
