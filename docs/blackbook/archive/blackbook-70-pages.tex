\begin{center}{\large\bfseries Abstract}\end{center}
\vspace{0.20in}
AI coding agents now read repositories, edit many files and execute shell commands with little human intervention. Run directly on a developer's machine, such an agent inherits the developer's privileges: it can read real secrets, write anywhere, contact any host and leave unreviewed changes in version control. Current tooling conflates running an agent with trusting its output. This project presents VaultShield, a pipeline that separates the two. VaultShield runs the agent in a disposable Docker container holding a fresh clone of the repository and a read-only credential file whose values mirror the shape of the developer's .env but contain no real secret; a repository-host token, when needed, is confined to the single git clone process. Terminal output, in-container file changes and policy violations are merged into a timestamped JSON Lines event log. Writes to off-limits paths fail the run, and an optional egress policy routes traffic through a hardened proxy that blocks and records non-allowlisted hosts. A separate hardened helper container then rebuilds the repository from a pre-agent base and commits the change to a dedicated branch with a structured diff, so the agent cannot falsify the evidence. Artifacts are uploaded to a Django REST Framework backend on MongoDB, scanned asynchronously, and approved or rejected by a reviewer in a React dashboard. Only an approved run can become a pull or merge request. The system comprises about 18,100 logical lines of product code. Of 2,704 automated tests, including Docker-backed isolation, egress, token-hygiene and tamper-resistance tests and concurrency tests against a real MongoDB replica set, 2,702 passed. In a 40-run benchmark, VaultShield added 1.17 seconds of fixed overhead per run by default and 1.98 seconds with egress allowlisting, a projected 0.4--0.7\% of a five-minute agent session; the host checkout was untouched and the change was captured in every run, with no container or network left behind. The evaluation also exposed limits: the shared-kernel boundary of containers, opt-in egress control, a polling file watcher that missed 20\% of very short writes, and an approval gate that is a workflow control rather than a separation-of-duties control in the single-user MVP. VaultShield shows that containment, evidence and human review for coding agents can be delivered together at negligible cost, with every residual risk stated explicitly.

\vspace{0.15in}
\noindent\textbf{Keywords:} AI coding agents, sandboxing, Docker, human-in-the-loop review, audit logging, credential isolation, egress control, software supply-chain security.

\chapter{Introduction}\label{introduction}

Large Language Models trained on source code have moved from completing a single line to operating as autonomous coding agents that read a repository, plan a change, edit many files, run shell commands and iterate on test results with little human intervention. Tools such as OpenAI Codex CLI, Google Antigravity, Amazon's Kiro and Anthropic's Claude Code expose this capability directly in the developer's terminal or editor, and research systems such as SWE-agent \cite{ref3} and OpenHands \cite{ref4} resolve a meaningful fraction of real GitHub issues from benchmarks like SWE-bench \cite{ref2}.

The same capability makes coding agents hazardous. An agent is an ordinary process that runs with the privileges of the user who launched it. On a developer's workstation it can read every secret in the shell environment and in nearby .env files, write anywhere the user can write, run commands the prompt never asked for, contact arbitrary hosts and leave changes in version control before anyone has examined them. Prior work shows that LLM-generated code is often insecure \cite{ref8}, that LLM-integrated applications can be hijacked through indirect prompt injection \cite{ref7}, and that even carefully aligned agents take risky actions in a non-trivial fraction of high-stakes scenarios \cite{ref5}. Governance guidance recommends constraining an agent's action space, requiring human approval for consequential actions and making agent activity legible \cite{ref9}, \cite{ref10}, but these recommendations are rarely packaged as a pipeline a developer can run against an existing repository.

VaultShield addresses that gap. It runs an AI coding agent inside a disposable Docker container, records what the agent does, captures the resulting code changes as a reviewable Git diff on a dedicated branch, and holds those changes behind an explicit human approval step before they can become a pull request or merge request. The developer's working tree, real credentials and repository write access are never handed to the agent. The system consists of a Python command-line interface that orchestrates the sandboxed run, a per-run Docker execution plane, and a Django REST Framework backend with a React dashboard where a reviewer approves or rejects the run. Producing evidence therefore never implies accepting it.

\section{Motivation}\label{motivation}

The first motivation is the asymmetry between the cost of an agent mistake and the cost of preventing it. An agent that deletes the wrong directory or commits a hard-coded key can cost hours of recovery, or far more if credentials leak, while running the same agent in a throwaway container costs about 1.2 seconds of fixed overhead per run on the evaluation machine.

The second motivation is credential exposure. Applications keep database strings, API keys and session secrets in a local .env file inside the very repository the agent is asked to modify. A preliminary spike in this project confirmed the risk: with no protection, a production coding agent asked to reveal a value from .env read the file with its built-in tool and printed both test secrets. Agent-specific deny rules reduced but did not remove the exposure, and only keeping the real value off disk proved reliable.

The third motivation is reviewability. Code review is the primary quality-control mechanism of modern software engineering \cite{ref14}, yet agent output often bypasses the pull-request workflow because it lands directly in the working tree. Capturing agent output on a dedicated branch, together with a timestamped event log and screenshots, lets a reviewer apply the same review process to agent changes and leaves a durable audit trail.

The fourth motivation is honest security engineering. Container isolation shares the host kernel and is not equivalent to a virtual machine boundary \cite{ref11}, \cite{ref12}, \cite{ref13}. VaultShield therefore states which controls it implements and which risks remain, so that adopters can judge where it fits in their own threat model.

\section{Problem Statement}\label{problem-statement}

Given a Git repository, a natural-language prompt and an AI coding agent, the problem is to let the agent attempt the requested change while guaranteeing that it never executes against the developer's real working tree, real application secrets or repository-host credentials; that everything it does is recorded as reviewable evidence; that its change is captured in a form it could not have tampered with; and that no change reaches a shared branch or pull request without an explicit human approval decision.

The agent must still be able to work, so it needs a real repository, a functioning toolchain and sometimes its own model API credential. The application must be able to start inside the sandbox for screenshots, so configuration values must keep their structural shape even though their content is fake. Every container, network and temporary branch must be removed on every exit path, and the pipeline overhead must stay small compared with typical agent run times.

\section{Objectives}\label{objectives}

The project set out to achieve the following objectives.
\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Develop a universal AI agent execution platform compatible with multiple AI coding agents and development environments through a common CLI interface.
\item
  Implement an intelligent Agentic AI Orchestrator that understands project context, asks clarification questions before execution, and provides enriched context to AI agents to improve accuracy and reduce hallucinations.
\item
  Ensure secure AI-assisted software development by executing AI agents inside isolated Docker-based sandbox environments while protecting production credentials and resources.
\item
  Provide comprehensive monitoring and automated security analysis by capturing AI activities, execution logs, code changes, and identifying security vulnerabilities or unsafe operations.
\item
  Enable transparent governance and human approval through a web-based dashboard that allows developers to review, verify, approve, or reject AI-generated changes before deployment.
\end{enumerate}

\section{Scope}\label{scope}

The scope of the VaultShield project covers the sandboxed execution, monitoring and human review of AI coding agents working on a Git repository.

\begin{itemize}
\tightlist
\item
  \textbf{Command-Line Interface:} the vaultshield CLI with the init, login, run, submit and teardown commands and the supporting protect command group.
\item
  \textbf{Sandboxed Execution:} a per-run Docker sandbox with a fresh clone, a read-only dummy credential file and guaranteed teardown.
\item
  \textbf{Agent Adapters:} the mock, codex, kiro and antigravity agents behind a common adapter interface.
\item
  \textbf{Monitoring and Egress Control:} terminal capture, in-container file watching, off-limits paths, a JSON Lines event log and an optional egress policy enforced by a hardened proxy.
\item
  \textbf{Trusted Change Capture:} the run branch and structured diff built in a separate hardened helper container, with run outputs scanned for leaked credentials.
\item
  \textbf{Backend, Dashboard and Submission:} a Django REST Framework backend on MongoDB with the run state machine and Celery-based scanning, a React review dashboard, and pull or merge request submission to GitHub or GitLab for approved runs.
\end{itemize}

The following are outside the scope of the project:

\begin{itemize}
\tightlist
\item
  \textbf{Stronger Isolation and Hosted Execution:} virtual-machine-grade isolation and running the CLI as a hosted service; container escape is a documented residual risk.
\item
  \textbf{Behavioural Judgement:} automatic analysis of agent intent, content-level network filtering and detection of deliberately encoded exfiltration.
\item
  \textbf{Multi-User Operation:} multi-tenant operation, role-based access control and separate runner and reviewer identities.
\item
  \textbf{Other Integrations:} live output streaming, other repository hosts, automatic merging and CI/CD pipeline integration.
\end{itemize}

The minimum viable product is scoped to a single developer's machine, so the approval gate is a workflow control within one trust domain rather than a security boundary between mutually distrustful parties.

\chapter{Literature Review}\label{literature-review}

The literature relevant to VaultShield falls into five overlapping strands: the capabilities and evaluation of autonomous coding agents, the security risks of LLM agents and of the code they generate, the governance and visibility of agentic systems, isolation technologies for running untrusted code, and human code review. Each strand is reviewed below, followed by a comparative analysis and a statement of the research gap that the project addresses.

Code-generating models and the need for sandboxes. Chen et al.~\cite{ref1} introduced Codex, a GPT model fine-tuned on public GitHub code, together with the HumanEval benchmark of hand-written programming problems scored by functional correctness. Because scoring functional correctness requires executing model-generated programs, the authors ran those programs inside a gVisor-based sandbox and discussed misuse, over-reliance and insecure code as broader risks. The paper established, at the start of the code-LLM era, that model output must be treated as untrusted code and executed only behind an isolation boundary. Its sandbox, however, was an internal evaluation harness for short, self-contained functions rather than a developer-facing tool for repository-scale changes with human review.

Repository-scale agents. Jimenez et al.~\cite{ref2} proposed SWE-bench, 2,294 task instances drawn from real GitHub issues and pull requests across twelve popular Python repositories, in which a model must produce a patch that makes the repository's failing tests pass. SWE-bench moved evaluation from isolated functions to whole repositories, and the best model of the time resolved fewer than 2\% of the issues. Yang et al.~\cite{ref3} then showed with SWE-agent that a purpose-built agent-computer interface, with dedicated commands for viewing, searching and editing files, raises this to 12.5\% with GPT-4 Turbo, executing inside a Docker container. Wang et al.~\cite{ref4} presented OpenHands, an open platform in which agents act through a sandboxed Docker runtime and every action and observation is recorded in an event stream. These systems validate two of VaultShield's design choices: a container is the practical execution environment for repository-scale agents, and a chronological record of agent actions is the natural unit of observability. Their sandboxes, however, exist to give the agent a reproducible workspace. None of them holds the agent's patch for human approval, and none keeps the developer's real secrets out of the workspace.

Risks of LLM agents. Ruan et al.~\cite{ref5} introduced ToolEmu, which uses a language model to emulate tool execution so that agents can be red-teamed against high-stakes scenarios without real side effects, together with an automatic safety evaluator. Across 36 toolkits and 144 test cases, even the safest agent they evaluated showed risky failures in 23.9\% of cases. Debenedetti et al.~\cite{ref6} built AgentDojo, a dynamic environment with 97 realistic tasks and 629 security test cases for measuring prompt-injection attacks against tool-using agents and the defences against them, and found that both remain far from solved. Greshake et al.~\cite{ref7} demonstrated indirect prompt injection, in which instructions planted in data that an LLM-integrated application retrieves take control of the application and can cause data exfiltration. For coding agents the implication is direct, because a repository's own files, issues and dependencies are untrusted input. These works characterise the threat convincingly, but they are evaluation frameworks and do not provide an operational containment and review pipeline for developers.

Security of AI-generated code. Pearce et al.~\cite{ref8} prompted GitHub Copilot with 89 scenarios based on MITRE's top Common Weakness Enumeration categories and found that about 40\% of the 1,689 generated programs contained vulnerabilities. This result motivates VaultShield's static security scan over every ingested diff and, more fundamentally, its requirement that a human reviews agent code before it is merged. The study evaluated completion suggestions rather than autonomous agents, so it does not cover agents that also execute commands; VaultShield extends the concern from insecure code to insecure behaviour.

Governance and visibility of agentic systems. Shavit et al.~\cite{ref9} proposed practices for keeping agentic AI systems safe and accountable, including evaluating suitability for a task, constraining the action space, requiring human approval for high-impact actions, setting safe defaults, making agent activity legible, automatic monitoring, attributability and interruptibility. Chan et al.~\cite{ref10} argued that oversight of AI agents depends on visibility and identified three categories of measures: agent identifiers, real-time monitoring and activity logging. VaultShield can be read as a concrete implementation of several of these practices for coding agents. The run identifier names the sandbox, the branch, the run directory and the backend record; the event log, egress log and screenshots form the activity log; and the approval state machine is the human-approval control. Both papers are deliberately technology-neutral, so they leave the engineering of such controls as an open problem.

Container isolation and its limits. Combe et al.~\cite{ref11} analysed Docker from a security perspective and identified the main areas of concern: isolation through Linux namespaces and control groups, the shared host kernel, network configuration and the trustworthiness of the image distribution chain. They concluded that Docker's default configuration offers reasonable isolation but that its security depends heavily on configuration. Agache et al.~\cite{ref12} described Firecracker, the virtual machine monitor behind AWS Lambda, whose microVMs boot in as little as 125 ms with under 5 MiB of memory overhead, showing that VM-grade isolation can approach container-like efficiency. Young et al.~\cite{ref13} measured gVisor, a user-space kernel that intercepts system calls to shrink the host kernel's attack surface, and showed that this stronger isolation carries substantial costs for system-call-heavy and file-system-heavy workloads. Together these papers frame VaultShield's trade-off: Docker containers are cheap and widely available but share the kernel, while gVisor and microVMs offer stronger boundaries at a cost in performance or operational complexity. VaultShield uses Docker for its MVP, documents the escape risk and lists gVisor and microVMs as future work.

Human code review. Bacchelli and Bird \cite{ref14} studied modern code review at Microsoft through observation, interviews and surveys. Although finding defects is the main stated motivation for review, much of its actual value lies in knowledge transfer, team awareness and alternative solutions, and the main challenge for reviewers is understanding the change and its context. This finding shapes VaultShield's dashboard: the reviewer receives not only the diff but also the timeline of what the agent did, screenshots of the running application and automated findings, so that understanding an agent's change does not require reconstructing its reasoning from the patch alone.

\section{Existing System}\label{existing-system}

Developers currently run AI coding agents in one of three ways. The most common is raw local execution, where the agent's CLI or editor extension runs in the developer's own checkout with the developer's environment, permissions and network access, and its changes appear as uncommitted edits. Some products add permission prompts or per-tool deny rules, but these are product-specific and often relaxed by users who find repeated prompts tedious. The second practice is ad-hoc containerisation, which usually bind-mounts the real working tree, so every write still lands on the host and the real .env file travels into the container. The third, development containers and cloud workspaces, is designed for convenience rather than for constraining an untrusted actor and holds nothing for review. Figure 3.1 summarises this workflow.

\section{Proposed System}\label{proposed-system}

VaultShield replaces this single step with a pipeline in which execution, evidence collection, storage and review are separate stages. The developer runs vaultshield run with an agent, a prompt and a repository URL. The CLI loads the project configuration, generates a run identifier, creates a per-run directory and registers the run with the backend before any container exists, so that later failures can be recorded. It then writes a dummy credential file that mirrors the shape of the developer's .env and resolves the agent adapter.

The CLI then creates a Docker container, mounts only the dummy credential file, clones the repository inside the container and installs dependencies. If egress control is enabled, the sandbox is moved onto an internal network whose only peer is a filtering proxy. Before any agent code runs, the CLI records the pre-agent commit through the Docker API as a trusted base. The agent runs under a pseudo-terminal while an in-container watcher records file changes, and both streams are merged into a timestamped event log; configured routes are screenshotted with a headless browser. The sandbox is then killed, and a separate hardened capture helper rebuilds the repository from the trusted base and a filtered copy of the work tree, commits the agent's changes to a dedicated run branch and computes the structured diff. Outputs are scanned for the agent's own credentials, the sandbox is torn down and the artifacts are uploaded, moving the run to awaiting\_\allowbreak{}review. A reviewer inspects the evidence in the dashboard and approves or rejects the run, and only an approved run can be submitted as a pull or merge request. Figure 3.2 presents this pipeline.

After a final secret check, the prompt is saved as prompt.md in the run directory, enters the unchanged sandboxed pipeline as the agent prompt, and is shown to the reviewer beside the diff and timeline; every model call is logged as metadata only. Because the Orchestrator sends project context to an external model and could be steered by hostile README text, it gains no privileges, its prompt is reviewed rather than trusted, and pattern-based sanitisation is a stated residual risk. Its effect on task success, approval rate and hallucinated content will be measured on real agents in Semester VIII.

\section{Critical Components of System Architecture}\label{critical-components-of-system-architecture}

The architecture has three planes: a host-side CLI pipeline, a per-run Docker execution plane, and a backend and dashboard review plane. The critical components are described below, together with the threats each one addresses.

\textbf{Threat model.}\label{threat-model} The protected assets are the developer's real secrets (application .env, SSH keys, repository-host token), the working tree and host, the shared repository, and the integrity of the evidence shown to the reviewer. The adversary is the agent and anything that can influence it: an agent that is simply wrong, one steered by indirect prompt injection in the repository's README, issues or dependencies \cite{ref7}, or a hostile agent binary or install script; it controls every process inside the sandbox. The host operating system and Docker daemon, the CLI, the capture-helper image, the backend and the repository host are trusted, and in the single-user system the developer and reviewer are one trust domain. Figure 3.5 marks the trust boundary around the untrusted sandbox and the attack paths T1 to T10, each classified below by STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Every mitigation named is implemented and tested in Semester VII; Semester VIII improvements appear only as residual risk. T1, prompt injection (T, I), is not prevented directly: its effects are contained by the controls below and by human approval of every change.

\subsection{Sandbox and Container Manager}\label{sandbox-and-container-manager}

The sandbox manager owns exactly one Docker container per run. It verifies that the credential file exists, creates a container named after the run, mounts the dummy credential file read-only, clones the repository inside the container and installs dependencies. The agent is executed through exec calls rather than as the container's main process, so the container's lifetime bounds every process the agent starts. For private repositories, the repository-host token is passed only as the environment of the single git clone process, so it never appears in the container's environment, the clone's Git configuration or any later process, and it is sent only to hosts on a strict per-provider allowlist. The Docker socket is never mounted.

\textit{Threats addressed.} T2, reading the real .env, SSH keys or home directory (I), fails because only the dummy file is mounted (TC-01, TC-02). T7, damage to the host or lingering processes (T, D), is contained by exec-only execution and guaranteed teardown, although no resource limits are set. T8, container escape (E), is narrowed because the Docker socket is never mounted and the capture helper drops all capabilities; the shared kernel and root user in the default sandbox remain residual risks, addressed by stronger isolation in Semester VIII.

When egress control is enabled, the EgressGuard builds the per-run topology shown in Figure 3.3: an internal network with no gateway, an ordinary bridge, and a hardened proxy attached to both. The sandbox is moved onto the internal network before the agent runs, so its only reachable peer is the proxy, which checks every destination host against the allowlist and logs each decision. This blocks T3, exfiltration over HTTP, raw TCP or DNS (I), in 4 of 4 tested cases (TC-03); egress is off unless enabled, and uploads to an allowlisted host remain possible.

Any error during creation removes the partial container and raises a single SandboxError whose message never contains a token. Teardown force-removes the container and is called from a finally block, so it runs on success, failure, timeout and interruption alike.

\subsection{Run Monitoring and Logging}\label{run-monitoring-and-logging}

The monitor produces the run's event log, events.jsonl, in which each line records an event type, a timestamp and a payload. The three event types are terminal output from the agent's pseudo-terminal, file changes observed by an in-container watcher, and violations such as off-limits writes, egress denials and leaked credentials. Each changed path is checked against the project's off-limits paths, and a match fails the run only after the log has been written, so evidence always outlives the failure. Browser capture starts the application inside the sandbox and takes one screenshot per configured route. Token hygiene scans the diff, the event log and changed files for the agent's own credential bytes; a hit fails the run, quarantines the diff and scrubs uploaded payloads.

\textit{Threats addressed.} T4, leakage of the repository token or the agent's model key into outputs (I), is detected for all five tested vectors (TC-06); deliberately encoded leaks remain residual. T6, edits to protected paths such as CI files (T), is recorded and fails the run (TC-04), but only for listed paths. The event log answers repudiation (R) by recording what the agent did; the polling watcher's missed writes are addressed by improved monitoring in Semester VIII.

\subsection{Diff Capture on a Dedicated Branch}\label{diff-capture-on-a-dedicated-branch}

If the branch and diff were built inside the agent's own sandbox, a hostile agent could tamper with Git state to misrepresent its changes. VaultShield therefore reads the pre-agent commit through the Docker API before the agent runs, and after the agent finishes it kills the sandbox and extracts a filtered archive of the work tree. A fresh capture helper container with no network, no capabilities and no environment rebuilds the repository from the trusted base, refuses unsafe Git configuration, commits every change to the run branch as exactly one commit, and writes diff.json with per-file additions, deletions and size-capped patches. The branch is exported as a Git bundle because the helper is destroyed at the end of the run. This defeats T5, tampering with Git state, hooks or configuration to hide a change (T, R), in both tested variants (TC-05).

The CLI may move a run from running to awaiting\_\allowbreak{}review or failed, and the approve and reject endpoints change the status only if it is still awaiting\_\allowbreak{}review, inside a MongoDB transaction that also creates the Approval record. Of two concurrent decisions exactly one succeeds, and the other receives HTTP 409 with the run's actual status.

\subsection{Backend API and Dashboard}\label{backend-api-and-dashboard}

The backend is a Django 5.2 project with Django REST Framework and MongoDB as its system of record. Every API path except login requires token authentication. The CLI registers runs, uploads events, diffs and screenshots, and patches the status; the dashboard reads run details and records decisions. Token authentication, the run identifier that binds sandbox, branch and record, and the bundle's SHA-256 limit T10, altered or misattributed evidence (T, S), although any holder of the API token can upload. The dashboard is a React 19 application built with Vite 7 that shows a projects overview, a filterable run history and a run detail page with Diff, Timeline, Screenshots and Security tabs and the decision controls.

\section{Project Development Methodology}\label{project-development-methodology}

VaultShield was developed with an iterative and incremental methodology based on specification-driven development. The team first wrote a requirements specification in which every requirement carried numbered acceptance criteria, and a design document with the architecture, data model and numbered correctness properties. The design was split into small, testable tasks, and each short iteration implemented a slice of tasks together with unit and property-based tests and, where isolation was involved, a Docker-backed integration test. The major phases were:

\begin{enumerate}
\tightlist
\item
  \textbf{Problem Study and Feasibility Spike:} survey the literature and measure how a production agent handles .env secrets under four protection configurations.
\item
  \textbf{Requirements and System Design:} write numbered requirements and define the architecture, run lifecycle, data model, REST API and threat model.
\item
  \textbf{CLI Core and Evidence Capture:} implement configuration, credential shaping, the sandbox lifecycle, agent adapters, monitoring, screenshots and Git capture.
\item
  \textbf{Backend and Dashboard:} implement the models, REST API, authentication, security scan, scheduled tasks and the review dashboard.
\item
  \textbf{Submission and Hardening:} implement PR and MR submission and teardown, then add the egress proxy, the trusted capture helper and token hygiene.
\item
  \textbf{Migration and Protect Module:} move the backend to MongoDB with transactional approval, and add the Protect module.
\item
  \textbf{Evaluation and Documentation:} run the tests and performance benchmark and write this report.
\end{enumerate}

\section{Effort Estimation Using COCOMO}\label{effort-estimation-using-basic-cocomo}

\subsection{Basic COCOMO Model}\label{basic-cocomo-model}

The Basic Constructive Cost Model \cite{ref15} estimates effort and schedule from size alone. VaultShield was classified as an organic project, built by a small team in a familiar environment with flexible requirements, so the coefficients are a = 2.4, b = 1.05, c = 2.5 and d = 0.38. E is effort in person-months, T is development time in months and P is the average number of persons.

E = a × (KLOC)\^{}b = 2.4 × (KLOC)\^{}1.05

T = c × (E)\^{}d = 2.5 × (E)\^{}0.38

P = E / T

\subsection{Calculation}\label{cocomo-calculation}

With KLOC = 18.07, (18.07)\^{}1.05 = 20.884, so E = 2.4 × 20.884 = 50.12 person-months. Then (50.12)\^{}0.38 = 4.426, so T = 2.5 × 4.426 = 11.06 months, and P = 50.12 / 11.06 = 4.53 persons. Table 4.4 summarises the estimate.

\section{Steps to Access the System}\label{steps-to-access-the-system}

The system requires Python 3.11 or later, a running Docker daemon, Git, Node.js 18 or later, a MongoDB replica set or Atlas cluster, and Playwright Chromium. The commands assume macOS or Linux.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Clone the repository and copy .env.example to .env, setting VAULTSHIELD\_\allowbreak{}MONGODB\_\allowbreak{}URL to the MongoDB connection string.
\item
  Start the backend and dashboard with docker compose up --build. The API is served on http://localhost:8000 and the dashboard on http://localhost:5173.
\item
  Create a user with docker compose exec web python manage.py createsuperuser.
\item
  Install the CLI:


cd cli \&\& python3 -m venv .venv \&\& source .venv/bin/activate \&\& pip install -e ''.[dev]'' \&\& playwright install chromium
\item
  Authenticate with vaultshield login --backend-url http://localhost:8000 --username <user>, create a project in the dashboard and note its identifier.
\item
  In a checkout of the target repository, run vaultshield init to write .vaultshield.yml.
\item
  Execute a sandboxed run, for example with the mock agent:


vaultshield run --agent=mock --prompt=''add a file'' --repo-url=''\$REPO'' --project ''\$PROJECT\_ID''
\item
  Open the dashboard, select the run, inspect the Diff, Timeline, Screenshots and Security tabs, and choose Approve or Reject.
\item
  For an approved run, run vaultshield submit <run-id> to open the pull or merge request; for a rejected run, run vaultshield teardown <run-id>.
\end{enumerate}

\subsection{Analysis of the Two Failed Tests}\label{failed-tests-analysis}

Both failing tests are Docker-backed tests in tests/\allowbreak{}test\_\allowbreak{}sandbox\_\allowbreak{}execution.py. Both exercise the interactive sign-in transport, which is used only when the antigravity agent is run with -\allowbreak{}-interactive-auth. This transport writes a pasted authorisation code to the agent's standard input through the Docker exec socket and redacts it from everything the CLI displays. Figure~\ref{fig:6-2} shows both failures re-run individually.

\begin{figure}[!htbp]
\centering
\SafeIncludeGraphics[width=0.85\textwidth,keepaspectratio]{images/evidence/ev-7-two-failures.png}
\par\medskip
\captionof{figure}{The two failing tests re-run individually, with their durations (excerpt)}\label{fig:6-2}
\end{figure}

\paragraph{Failure 1: interactive sign-in timeout.} The test test\_\allowbreak{}a\_\allowbreak{}hanging\_\allowbreak{}signin\_\allowbreak{}hits\_\allowbreak{}the\_\allowbreak{}read\_\allowbreak{}timeout\_\allowbreak{}instead\_\allowbreak{}of\_\allowbreak{}blocking\_\allowbreak{}forever starts a fake sign-in program in a real container that prints the code prompt and then hangs. The test shortens the read deadline to 3 seconds and expects the CLI to give up within 60 seconds. The read deadline is set as a socket timeout on the exec stream, and on Docker Desktop 29.2.1 that timeout does not interrupt the blocking read, so the read blocked for 600.33 seconds until the fake program exited. This is a genuine availability defect in the optional interactive authentication flow: a sign-in that stops responding keeps the CLI waiting instead of failing after the deadline. It exposes no secret, because the code is still redacted and teardown still runs, which other passing tests verify. A watchdog-based deadline that kills the exec independently of the socket is planned.

\paragraph{Failure 2: redacted echo expectation.} The test test\_\allowbreak{}exec\_\allowbreak{}interactive\_\allowbreak{}really\_\allowbreak{}delivers\_\allowbreak{}stdin\_\allowbreak{}to\_\allowbreak{}a\_\allowbreak{}container\_\allowbreak{}process sends a sentinel value to a container process that prints RECEIVED:[value], and expects the raw value in the output. The actual output was RECEIVED:[***]. Redaction replaces only an exact match of the sent value, so this output proves that the process received exactly the bytes sent and that the terminal echo was then masked. The masking is intentional credential protection that keeps an authorisation code off the terminal and out of the logs. The test predates the redaction, so its expectation is outdated and should be changed to the redacted form.

\paragraph{Reliability impact.} The two failures are about 0.07\% of the 2,704 tests of the original campaign. They are of different kinds. Failure 1 is a genuine functional defect: the code does not do what it is specified to do, and a user of the optional sign-in flow can observe it. Failure 2 is an outdated test assertion: the code behaves as specified and only the test's expectation is wrong, so it is not a functional or security defect. Neither affects the default execution workflow, which does not use the interactive transport. The security-critical isolation, secret-substitution, egress, trusted-capture, token-hygiene and approval tests all passed; they drive the sandbox through the ordinary non-interactive exec path that every default run uses, so a defect in the optional sign-in path cannot hide a failure in them.

Of 2,704 automated tests in the Semester VII campaign, 2,702 passed, and every security-critical behaviour named in the objectives was exercised against real infrastructure. \section{Case Study: Analysis of Real Runs}\label{case-study-analysis-of-real-runs}

The repository preserves five complete mock-agent runs from development. In one of the five runs, however, the event log has no file-change event even though the diff and screenshot both show the file, the same gap seen in 8 of the 40 benchmark runs. \section{Chapter Summary}\label{chapter-summary}

With the mock agent, the default pipeline completed in 1.403 s on average, adding 1.166 s to direct execution, with trusted capture the largest stage; real-agent timings remain to be measured. Isolation, change capture and cleanup succeeded in every evaluated run, all injected unsafe behaviours were blocked or detected, and every value in six real sandbox credential files was a dummy. The file watcher recorded the agent's change in 80\% of runs, confirming the trusted diff as the authoritative record.

\chapter{Conclusion}\label{conclusion}

VaultShield separates running an AI coding agent from trusting what it produces. The agent receives a disposable Docker container, a fresh clone and only dummy credentials; its output, file changes and network decisions are recorded in an event log; its change is captured as one commit on a dedicated branch by a separate hardened container; and the change can become a pull or merge request only after a human approves it in the review dashboard. The system was built as a Python CLI, a Django REST Framework backend on MongoDB with Celery workers, and a React dashboard, totalling about 18.1 thousand logical lines of product code. \chapter{Future Scope}\label{future-scope}

The limitations identified in this report define the future work. The first four items are the committed Semester VIII enhancements, each tied to a limitation found in the evaluation; the remaining items are longer-term work.

\medskip\noindent\textbf{Semester VIII enhancements}\label{sem8-enhancements}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Agentic AI Orchestrator:} implement the design in Section~\ref{proposed-orchestrator}, which scans the project, asks clarifying questions before execution and passes a sanitised, enriched prompt to the agent, then measure on real agents whether it raises task success and approval rates and reduces hallucinated files, functions and packages. This completes Objective 2.
\item
  \textbf{Stronger Sandbox Isolation:} run the sandbox by default as a non-root user with all capabilities dropped, no-new-privileges and CPU, memory and process limits; make egress default-deny; and support gVisor or Firecracker microVM runtimes \cite{ref12}, \cite{ref13}. This addresses the shared-kernel and opt-in egress limitations (threats T3, T7 and T8 in Section~\ref{threat-model}).
\item
  \textbf{Improved Monitoring:} replace the polling file watcher, which missed 8 of 40 short writes, with an event-driven watcher; cross-check the event log against the trusted diff; stream events live so a reviewer can interrupt a run \cite{ref9}; render patch text in the Diff tab; and enforce the interactive sign-in deadline with a watchdog (Section~\ref{failed-tests-analysis}).
\item
  \textbf{Role-Based Approval:} add separate developer and reviewer accounts, role-based access control, decision attribution and optional multiple approvals, and route every status transition through the gated approval endpoint, so that the approval gate becomes a separation-of-duties control rather than a single-user workflow control (threat T9).
\end{enumerate}

\noindent\textbf{Further long-term work}

\begin{itemize}
\tightlist
\item
  \textbf{Policy Engine:} express rules such as required approvals for infrastructure files or approved dependency lists declaratively, with path-aware egress filtering.
\item
  \textbf{Cost and Resource Controls:} record per-run token usage and enforce per-project budgets and sandbox time limits.
\item
  \textbf{Multi-Repository and Parallel Runs:} capture one branch per repository in a single run, and let several agents attempt the same task for the reviewer to compare.
\item
  \textbf{IDE Integration and Evidence Quality:} start and review runs from the editor, and scan screenshots for credentials.
\item
  \textbf{Broader Evaluation:} extend the real-agent evaluation to a subset of SWE-bench \cite{ref2} and to adaptive red-team attacks, with a usability study with reviewers.
\end{itemize}
